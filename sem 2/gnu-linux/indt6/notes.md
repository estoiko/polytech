# Linux лаб №6 - tmpfs

## Что такое `tmpfs`?

`tmpfs` - файловая система в виртуальной памяти [^1]

Свойство tmpfs позволяет создавать файловые системы, чьё содержимое находится в виртуальной памяти. 

Так как файлы в таких файловых системах, обычно, располагаются в оперативной памяти, то доступ к файлах очень быстро.

Файловая система создаётся автоматически при монтировании с типом  tmpfs  с  помощью  команды  следующего вида:

```sh
 sudo mount -t tmpfs -o size=10M tmpfs /mnt/mytmpfs
```

Файловая система (ФС) в Linux — это упорядоченный способ организации, хранения и именования данных, 
предоставляющий ядру ОС единый интерфейс для работы с файлами, независимо от того, 
находятся ли они на диске, в оперативной памяти (как tmpfs) или генерируются виртуально (procfs). 
Она определяет структуру каталогов, права доступа и метаданные. 

Основные типы файловых систем в Linux:
- Дисковые (постоянные): ext4 (стандарт), XFS, Btrfs, F2FS.
- Виртуальные/Оперативные (временные): tmpfs (хранит данные в ОЗУ/swap, очищается при перезагрузке), ramfs.
- Специальные (системные): procfs (информация о процессах), sysfs (информация о ядре и устройствах).
- Сетевые: NFS, CIFS/SMB. 

Ключевые особенности:
- Единое дерево: В Linux нет букв дисков (C:, D:); все ФС монтируются как папки в единой иерархии, начинающейся с корня /.
- tmpfs: В отличие от реального диска, она работает в разы быстрее, 
так как не нуждается в постоянной записи на носитель, а размер динамически меняется в зависимости от объема занятой памяти.
- Прозрачность: Для пользователя и программ разница между чтением файла с жесткого диска или из виртуальной памяти (tmpfs) минимальна — 
это всё файлы

## Свойства файловой системы `tmpfs`

•  Файловая  система  может  задействовать  пространство  подкачки,  если это требуется из-за нагрузки на физическую память.

•  Файловая система потребляет физическую память и пространство подкачки  только  для  хранения  текущего содержимого файловой системы.

•  При  операции  перемонтирования (mount -o remount), размер файловой системы можно изменить (без потери имеющегося содержимого файловой системы).

При размонтировании файловой системы `tmpfs` её содержимое уничтожается (теряется).

## Что такое дисковый кэш в Linux

При чтении файл с диска, ядро не выбрасывает его из RAM после использования — оно оставляет его в `page cache`. При следующем обращении к тому же файлу данные берутся из RAM, а не с диска. 

При сборке ядра компилятор читает тысячи `.c` и `.h` файлов. Если ты уже собирал один раз — все эти файлы уже лежат в `page cache`. Вторая сборка будет быстрее не потому что `tmpfs` лучше, а потому что диск почти не читается — всё и так в памяти.


## Три вида кэша в Linux

`Page cache` — самый большой. Хранит содержимое файлов, которые недавно читались или писались.

`Dentries` (dentry cache) — кэш директорных записей. Хранит результаты поиска имён файлов: ядро помнит что /home/host/linux-6.8.0/kernel/sched/core.c существует и где он находится, не обращаясь каждый раз к диску за этой информацией.

`Inodes` — кэш метаданных файлов: размер, права, время изменения, указатели на блоки данных. Без этого кэша на каждый файл нужно лезть на диск за служебной информацией.

## Команда для очистки кэша

```sh
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches
```

Разберём по частям:

**sync** — сначала сбрасывает все "грязные" (dirty) страницы на диск. Dirty-страницы — это данные, которые уже записаны в page cache, но ещё не на физический диск. Если сразу дропнуть кэш без sync — можно потерять данные, которые ещё не успели записаться.

**/proc/sys/vm/drop_caches** — это не обычный файл, а псевдофайл в виртуальной файловой системе procfs. Запись в него — это по сути системный вызов к ядру с командой что именно очистить. Цифра определяет что именно дропать:
- 1 — только page cache
- 2 — только dentries и inodes
- 3 — всё сразу (page cache + dentries + inodes)

Поэтому 3 — самый полный вариант для честного бенчмарка.

**tee вместо >** — потому что sudo echo 3 > /proc/sys/vm/drop_caches не сработает. Перенаправление > выполняется текущим шеллом *до* sudo, то есть файл пытается открыть твой пользователь, а не root. tee же сам пишет в файл уже с правами sudo.

### Схема 

```txt
Первая сборка (холодный кэш) → медленно, всё читается с диска
                    ↓
         файлы оседают в page cache
                    ↓
Вторая сборка (горячий кэш) → быстрее, данные берутся из RAM
                    ↓
      результат нечестный — ты меряешь кэш, а не tmpfs
Поэтому перед каждым запуском: sync && echo 3 | sudo tee /proc/sys/vm/drop_caches — и обе сборки стартуют в одинаковых условиях.
```
